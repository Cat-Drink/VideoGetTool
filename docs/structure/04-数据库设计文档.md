## 2. 数据库概述

### 2.1 数据库选型

本项目采用 **SQLite** 作为唯一持久化存储，并启用 **WAL（Write-Ahead Logging）模式**。

| 选项 | 决策 | 理由 |
|---|---|---|
| 数据库引擎 | SQLite 3.x | 轻量、无需安装独立服务进程、随应用分发；对单机桌面应用场景足够 |
| 日志模式 | `PRAGMA journal_mode=WAL` | 读写并发性能优于 DELETE 模式（默认），UI 读进度与工作线程写进度不互斥 |
| 同步模式 | `PRAGMA synchronous=NORMAL` | WAL 模式下 NORMAL 已足够安全，且显著优于 FULL 的写入吞吐 |
| 外键约束 | `PRAGMA foreign_keys=ON` | 启用 `ON DELETE CASCADE` 等外键行为，依赖应用层显式开启 |
| 连接方式 | 单文件多连接 | Qt 主线程与 asyncio 工作线程各持独立连接，避免跨线程使用同一连接 |

> **不选型理由**：
> - 不选 MySQL/PostgreSQL：要求用户额外安装数据库服务，违反"双击即用"的非技术用户发布目标。
> - 不选纯 JSON 文件存储：任务规模增长后查询/并发写入性能差，且无法保证原子性。

### 2.2 数据库文件位置

数据库文件统一存放于 Windows 用户级应用数据目录，与可执行程序解耦：

```
%APPDATA%\DouyinCatcher\
├── data.db          # SQLite 主数据库文件
├── data.db-wal      # WAL 日志文件（运行时生成）
├── data.db-shm      # 共享内存文件（运行时生成）
└── logs\
    └── app.log      # 应用日志（按天滚动，保留 7 天）
```

**路径解析规则**：
- 通过 Python `os.environ['APPDATA']` 拼接 `DouyinCatcher\data.db` 得到绝对路径。
- 程序目录只放代码与资源，不存放用户数据，确保卸载/重装不丢用户数据。
- 首次启动时若目录或文件不存在，由应用自动创建目录并初始化 schema。

### 2.3 字符编码与排序规则

| 属性 | 值 | 说明 |
|---|---|---|
| 数据库编码 | UTF-8 | SQLite 默认即为 UTF-8，支持中文文案、作者昵称、标签等 |
| 文本排序规则 | `NOCASE`（仅用于标识符比较） / 默认 `BINARY`（业务字段） | 业务字段保持 `BINARY` 以保留精确匹配行为，避免大小写折叠影响 aweme_id 等敏感字段 |
| 日期格式 | ISO 8601 字符串（`YYYY-MM-DDTHH:MM:SS.sssZ`） | 文本存储，便于跨平台与人类可读；比较时按字符串字典序即等价于时间顺序 |
| 布尔表达 | INTEGER（0=false，1=true） | SQLite 无原生 BOOL 类型 |
| 时间戳 | `created_at` / `updated_at` 均为 ISO 8601 文本 | 应用层在每次 UPDATE 时刷新 `updated_at` |

## 3. ER 关系图

以下用 ASCII 文本描述 5 张表之间的关系。所有"一对多"关系通过外键 + `ON DELETE CASCADE` 维护；"一对一"通过外键 + 唯一索引实现。

```
┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
│      tasks       │  1 : N  │   task_items     │  1 : 1  │    metadata      │
│  (下载任务表)     ├────────►│   (任务项表)      ├────────►│  (作品元数据表)   │
│                  │         │                  │         │                  │
│  id (PK)         │         │  id (PK)         │         │  id (PK)         │
│  source_type     │         │  task_id (FK)    │         │  task_item_id(FK)│
│  source_url      │         │  aweme_id        │         │  aweme_id        │
│  status          │         │  url             │         │  title/desc      │
│  total_items     │         │  type            │         │  author          │
│  completed_items │         │  status          │         │  publish_time    │
│  download_dir    │         │  downloaded_bytes│         │  *_count         │
│  created_at      │         │  total_bytes     │         │  tags (JSON)     │
│  updated_at      │         │  retry_count     │         │  raw_json        │
└──────────────────┘         │  local_path      │         └──────────────────┘
                             │  ...             │
                             └────────┬─────────┘
                                      │
                                      │ ON DELETE CASCADE
                                      │ (task 删除 → 子项级联删除)
                                      ▼
                             (metadata 同样级联：task_item 删除 → metadata 删除)


┌──────────────────┐                       ┌──────────────────┐
│     cookies      │   独立表（无外键）      │     config       │
│   (Cookie 池表)   │                       │  (应用配置表)     │
│                  │                       │                  │
│  id (PK)         │                       │  key (PK)        │
│  content         │                       │  value           │
│  label           │                       │                  │
│  status          │                       │  onboarding_done │
│  last_used       │                       │  download_dir    │
│  last_check      │                       │  concurrency     │
│  fail_count      │                       │  chunk_size      │
│  created_at      │                       │  metadata_format │
└──────────────────┘                       └──────────────────┘
```

**关系汇总表**：

| 父表 | 子表 | 关系 | 外键字段 | 删除行为 |
|---|---|---|---|---|
| tasks | task_items | 1 : N | task_items.task_id → tasks.id | ON DELETE CASCADE |
| task_items | metadata | 1 : 1 | metadata.task_item_id → task_items.id | ON DELETE CASCADE |
| cookies | （无） | — | — | — |
| config | （无） | — | — | — |

> **说明**：`metadata` 表的 1:1 关系通过在 `metadata.task_item_id` 上加唯一索引实现，但当前 schema 未显式加 UNIQUE 约束，由应用层保证"一个 task_item 至多对应一条 metadata"。

## 4. 表结构详细设计

### 4.1 tasks 表（下载任务表）

**用途**：一次抓取/下载请求对应一条记录。可能是单链接、批量链接、用户主页抓取或文件导入。

#### 4.1.1 字段说明

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 任务主键，全局唯一 |
| source_type | TEXT | NOT NULL | — | 任务来源类型，枚举值：`single`（单链接）/ `batch`（批量链接粘贴）/ `user_home`（用户主页抓取）/ `file_import`（文件导入链接列表） |
| source_url | TEXT | — | NULL | 原始链接。批量/文件导入时可为 NULL 或保存首个链接；主页抓取时是主页 URL |
| status | TEXT | NOT NULL | — | 任务状态，枚举值：`pending` / `downloading` / `paused` / `completed` / `failed`。详见 4.1.2 状态机 |
| total_items | INTEGER | — | 0 | 该任务下的子项总数。解析完成后写入；下载过程中不变 |
| completed_items | INTEGER | — | 0 | 已完成子项数。每有一个 task_item 转 completed 时 +1 |
| created_at | TEXT | NOT NULL | — | 任务创建时间，ISO 8601 格式 |
| updated_at | TEXT | NOT NULL | — | 任务最近更新时间，ISO 8601 格式。每次状态/计数变化时刷新 |
| download_dir | TEXT | NOT NULL | — | 该任务的下载目录（绝对路径）。同一任务所有子项存于此目录 |

#### 4.1.2 状态机图

```
                          [用户提交链接/导入文件]
                                    │
                                    ▼
                              ┌──────────┐
                              │ pending  │  任务已创建，子项尚未进下载队列
                              └────┬─────┘
                                   │ 调度器取出子项开始下载
                                   ▼
                              ┌──────────────┐
                ┌─────────►  │ downloading  │  至少有一个子项在下载
                │             └──────┬───────┘
                │                    │
                │   ┌────────────────┼────────────────┐
                │   │ 用户暂停        │ 全部子项完成     │ 全部子项失败或重试耗尽
                │   ▼                ▼                 ▼
                │ ┌────────┐   ┌───────────┐   ┌────────┐
                │ │ paused │   │ completed │   │ failed │
                │ └────┬───┘   └───────────┘   └────────┘
                │      │ 用户点"开始"
                │      └──────────► (回到 downloading)
                │
                └─── (部分子项失败但仍可继续) ──┘
```

**状态定义**：

| 状态 | 含义 | 进入条件 | 退出条件 |
|---|---|---|---|
| pending | 任务已创建，等待调度器拉取子项 | 用户提交新任务 | 调度器开始处理任一子项 |
| downloading | 任务正在下载中（至少一个子项处于下载态） | 调度器从 pending 拉起 | 全部子项完成 / 用户暂停 / 全部失败 |
| paused | 用户主动暂停 | 用户点击"暂停" | 用户点击"开始" |
| completed | 任务下所有子项均为 completed | 最后一个子项转 completed | 终态（除非用户手动重置） |
| failed | 任务下所有子项均失败（重试耗尽） | 最后一个失败子项转 failed | 终态（除非用户手动重试） |

> **说明**：当一个任务同时存在已完成和失败子项时，按"全部子项失败 → failed；否则只要有一个完成则倾向于 completed"的策略判定，具体由应用层在每次子项状态变更后聚合判定。

### 4.2 task_items 表（任务项表）

**用途**：一个视频/图集对应一条记录，是断点续传的核心载体。

#### 4.2.1 字段说明

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 子项主键 |
| task_id | INTEGER | NOT NULL, REFERENCES tasks(id) ON DELETE CASCADE | — | 所属任务 ID |
| aweme_id | TEXT | — | NULL | 抖音作品 ID，用于去重判定。可能为空（解析失败时） |
| url | TEXT | NOT NULL | — | 解析出的无水印直链 |
| title | TEXT | — | NULL | 作品标题 |
| author | TEXT | — | NULL | 作者昵称 |
| author_sec_id | TEXT | — | NULL | 作者 sec_user_id，便于按作者聚合 |
| type | TEXT | NOT NULL | — | 作品类型枚举：`video`（视频）/ `image_set`（图文图集）/ `long_video`（长视频） |
| duration | TEXT | — | NULL | 时长文本，如 `15s` / `12:30`。仅用于 UI 展示 |
| image_count | INTEGER | — | NULL | 图集图片数，仅 `type='image_set'` 时有值 |
| cover_url | TEXT | — | NULL | 封面图 URL，用于 UI 列表缩略图 |
| status | TEXT | NOT NULL | — | 子项状态：`pending` / `downloading` / `paused` / `completed` / `failed`。详见 4.2.2 |
| downloaded_bytes | INTEGER | — | 0 | 已下载字节数（单文件分块续传用），详见 4.2.3 |
| total_bytes | INTEGER | — | 0 | 文件总大小（字节）。从 HTTP `Content-Length` 或 `Content-Range` 获取 |
| retry_count | INTEGER | — | 0 | 已重试次数，上限 3。每次失败 +1 |
| fail_reason | TEXT | — | NULL | 失败原因（人话描述），如 "Cookie 失效或被限流，请更新 Cookie" |
| local_path | TEXT | — | NULL | 下载完成后的本地文件绝对路径（不含 `.part` 后缀） |
| created_at | TEXT | NOT NULL | — | 子项创建时间，ISO 8601 |
| updated_at | TEXT | NOT NULL | — | 子项最近更新时间，ISO 8601 |

#### 4.2.2 状态机图

```
                        [解析成功，写入 task_items]
                                  │
                                  ▼
                            ┌──────────┐
                ┌────────►  │ pending  │  等待调度器调度
                │           └────┬─────┘
                │                │ 调度器取出，分配下载槽
                │                ▼
                │           ┌──────────────┐
                │           │ downloading  │  正在下载（httpx Range 流式）
                │           └──────┬───────┘
                │                  │
                │   ┌──────────────┼──────────────┬───────────────┐
                │   │ 用户暂停      │ 下载完成       │ 单次失败且     │ 单次失败且
                │   │ / 应用关闭    │ (Range 拉完)   │ retry<3       │ retry==3
                │   ▼              ▼                ▼               ▼
                │ ┌────────┐  ┌───────────┐  ┌──────────┐    ┌────────┐
                │ │ paused │  │ completed │  │ pending  │    │ failed │
                │ └───┬────┘  └───────────┘  └────┬─────┘    └────────┘
                │     │                          │ 指数退避后
                │     │ 用户点"开始"             │ 重新入队
                │     └──────► downloading ◄─────┘
                │
                └─── (应用重启时 downloading → paused，见 6.2) ──┘
```

**状态定义**：

| 状态 | 含义 | 关键行为 |
|---|---|---|
| pending | 待下载或重试等待中 | 调度器从中取出可执行项 |
| downloading | 正在下载 | httpx Range 流式写 `.part` 文件，每 5s/1MB 刷新 `downloaded_bytes` |
| paused | 暂停（用户主动或应用重启） | 保留 `.part` 与 `downloaded_bytes`，等待恢复 |
| completed | 下载完成 | `.part` 已重命名为最终文件，`local_path` 已写入 |
| failed | 重试耗尽（3 次） | `fail_reason` 已写入，需用户手动重置才能再试 |

#### 4.2.3 断点续传字段说明

| 字段 | 协同机制 |
|---|---|
| `downloaded_bytes` | 已下载字节数。下载中每 5 秒或每 1MB 持久化一次，防止崩溃丢失进度。续传时作为 HTTP `Range: bytes={downloaded_bytes}-` 的起始值 |
| `total_bytes` | 文件总大小。首次响应通过 `Content-Range` 或 `Content-Length` 获取并持久化，用于计算进度百分比与校验完整性 |
| `local_path` | 下载完成后写入最终路径（不含 `.part`）。续传时根据 `local_path + '.part'` 找到临时文件 |
| `.part` 文件 | 本地临时文件机制：下载时文件名为 `<local_path>.part`；完成后 `rename` 去掉后缀。详见 6.3 |

**续传判定流程**：
1. 子项进入 `downloading` 时，检查磁盘上 `<local_path>.part` 是否存在
2. 存在 → 读取 `downloaded_bytes`，发 `Range: bytes={downloaded_bytes}-` 请求
3. 服务器返回 206 → 追加写入 `.part` 文件
4. 服务器返回 200（不支持 Range）→ 从头下载，清空 `.part`
5. 不存在 → 从 0 开始下载，新建 `.part` 文件

### 4.3 metadata 表（作品元数据表）

**用途**：保存作品元数据，用于数据分析与历史回溯。一个 task_item 至多对应一条 metadata。

#### 4.3.1 字段说明

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | 元数据记录主键 |
| task_item_id | INTEGER | NOT NULL, REFERENCES task_items(id) ON DELETE CASCADE | — | 关联的 task_items.id |
| aweme_id | TEXT | — | NULL | 抖音作品 ID（与 task_items.aweme_id 冗余存储，便于脱离子项独立查询） |
| title | TEXT | — | NULL | 作品标题 |
| desc | TEXT | — | NULL | 视频文案（description） |
| author | TEXT | — | NULL | 作者昵称 |
| author_uid | TEXT | — | NULL | 作者 UID |
| publish_time | TEXT | — | NULL | 作品发布时间，ISO 8601 格式 |
| like_count | INTEGER | — | NULL | 点赞数 |
| comment_count | INTEGER | — | NULL | 评论数 |
| share_count | INTEGER | — | NULL | 分享数 |
| collect_count | INTEGER | — | NULL | 收藏数 |
| tags | TEXT | — | NULL | 标签 JSON 数组，如 `["旅行","海边"]` |
| raw_json | TEXT | — | NULL | 原始 API 返回 JSON 字符串，调试/扩展用 |

> **冗余说明**：`aweme_id`、`title`、`author` 等字段在 task_items 与 metadata 中均存在，是有意冗余：

> - metadata 用于完整保留作品信息（含计数、标签、原始 JSON），即使 task_items 被清理仍可独立查询

### 4.4 cookies 表（Cookie 池表）

**用途**：管理多 Cookie 轮换池，支持健康检查与负载均衡。

#### 4.4.1 字段说明

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增 | Cookie 记录主键 |
| content | TEXT | NOT NULL | — | Cookie 字符串完整内容 |
| label | TEXT | — | NULL | 用户自定义标签，如"账号1"，便于识别 |
| status | TEXT | NOT NULL | — | Cookie 健康状态：`untested` / `valid` / `invalid`。详见 4.4.2 |
| last_used | TEXT | — | NULL | 最后一次被请求使用的时间，ISO 8601。用于"最久未用优先"调度 |
| last_check | TEXT | — | NULL | 最后一次主动测试时间，ISO 8601 |
| fail_count | INTEGER | — | 0 | 连续失败次数。请求成功时清零；连续 3 次失败置 `invalid` |
| created_at | TEXT | NOT NULL | — | Cookie 添加时间，ISO 8601 |

#### 4.4.2 Cookie 健康状态流转

```
                  [用户添加新 Cookie]
                          │
                          ▼
                    ┌───────────┐
                    │ untested  │  尚未测试或使用
                    └─────┬─────┘
                          │ 用户点"测试" / 调度器首次使用
                          ▼
                    ┌───────────┐
              ┌───► │  valid    │  测试通过，可参与轮询
              │     └─────┬─────┘
              │           │ 请求返回 461/412，fail_count += 1
              │           ▼
              │     ┌─────────────────┐
              │     │ fail_count < 3  │  仍为 valid，但累积失败
              │     └────────┬────────┘
              │              │ fail_count == 3
              │              ▼
              │        ┌───────────┐
              │        │  invalid  │  已失效，不再参与轮询
              │        └─────┬─────┘
              │              │ 用户重新粘贴新 Cookie 并测试通过
              │              ▼
              └──────── (更新 content，重置 fail_count=0，status=valid)
```

**状态定义**：

| 状态 | 含义 | 是否参与请求调度 |
|---|---|---|
| untested | 刚添加，尚未验证 | 否（首次使用前应先测试） |
| valid | 健康，可参与轮询 | 是 |
| invalid | 已失效（连续失败 3 次或主动测试失败） | 否 |

**调度策略**：
- 每次请求从池里取 `status='valid'` 且 `last_used` 最早的 Cookie（最久未用优先，均衡负载）
- 取到后更新 `last_used` 为当前时间
- 池里所有 Cookie 均为 `invalid` → 暂停所有任务，弹窗提示"所有 Cookie 已失效，请更新"

### 4.5 config 表（应用配置表）

**用途**：键值对存储非敏感应用配置。

#### 4.5.1 字段说明

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| key | TEXT | PRIMARY KEY | — | 配置键名，唯一 |

## 5. 索引设计

### 5.1 索引清单

| 索引名 | 表 | 字段 | 用途 | 创建语句 |
|---|---|---|---|---|
| idx_tasks_status | tasks | status | 按状态筛选任务列表（如"下载中"、"失败"过滤） | `CREATE INDEX idx_tasks_status ON tasks(status);` |
| idx_task_items_task_id | task_items | task_id | 父任务关联查询（加载某任务下所有子项） | `CREATE INDEX idx_task_items_task_id ON task_items(task_id);` |
| idx_task_items_status | task_items | status | 调度器扫描待下载/暂停/失败子项 | `CREATE INDEX idx_task_items_status ON task_items(status);` |
| idx_task_items_aweme_id | task_items | aweme_id | 去重查询：加入队列前检查是否已存在 completed 记录 | `CREATE INDEX idx_task_items_aweme_id ON task_items(aweme_id);` |
| idx_cookies_status | cookies | status | Cookie 池轮询：快速取 `status='valid'` 的记录 | `CREATE INDEX idx_cookies_status ON cookies(status);` |
| idx_metadata_task_item_id | metadata | task_item_id | 按 task_item 查询元数据 | `CREATE INDEX idx_metadata_task_item_id ON metadata(task_item_id);` |
| idx_subscriptions_enabled | subscriptions | enabled | 扫描器快速取启用订阅 | `CREATE INDEX idx_subscriptions_enabled ON subscriptions(enabled);` |
| idx_subscription_items_sub_id | subscription_items | subscription_id | 按订阅查询作品列表 | `CREATE INDEX idx_subscription_items_sub_id ON subscription_items(subscription_id);` |
| idx_subscription_items_status | subscription_items | status | 按状态（如 new）筛选作品 | `CREATE INDEX idx_subscription_items_status ON subscription_items(status);` |

### 5.2 设计说明

- **不建多余索引**：SQLite 单机场景写入代价高于查询，索引数量克制。
- **未加唯一索引**：`task_items.aweme_id` 与 `metadata.task_item_id` 的唯一性由应用层保证（去重逻辑在加入队列前判定）。
- **主键自动索引**：所有 `PRIMARY KEY` 字段（`tasks.id`、`task_items.id`、`metadata.id`、`cookies.id`、`config.key`）自动建索引，无需显式声明。

## 6. 数据生命周期管理

### 6.1 任务队列续传机制（启动时 scanning 逻辑）

应用启动时执行以下扫描逻辑，重建下载队列：

```
应用启动
   │
   ▼
[扫描 tasks 表]  WHERE status IN ('pending','downloading','paused','failed')
   │
   ├─ pending    ──► 直接加入待调度队列
   ├─ paused     ──► 加入待调度队列，等待用户点"开始"或自动继续
   ├─ downloading──► 重置为 paused（见 6.2），加入待调度队列
   └─ failed     ──► 不自动重试，UI 标红显示，等用户手动操作
   │
   ▼
[扫描 task_items 表]  WHERE status IN ('pending','downloading','paused')
   │
   ├─ pending    ──► 加入调度器待下载队列
   ├─ paused     ──► 加入调度器待下载队列（保持 paused，等用户恢复）
   └─ downloading──► 重置为 paused（见 6.2），保留 .part 与 downloaded_bytes
   │
   ▼
[检查磁盘 .part 文件]
   │
   ├─ .part 存在且 downloaded_bytes > 0 ──► 续传准备就绪
   ├─ .part 存在但 downloaded_bytes == 0  ──► 正常从头下载
   └─ .part 不存在但 downloaded_bytes > 0  ──► 重置 downloaded_bytes=0（数据与磁盘不一致）
   │
   ▼
[调度器就绪，等待用户操作或自动继续]
```

### 6.2 downloading → paused 重置规则

应用异常退出或正常关闭时，可能存在 `status='downloading'` 的记录。重启后这些记录无法继续下载（原 asyncio 任务已销毁），需统一重置：

| 表 | 重置规则 | 理由 |
|---|---|---|
| tasks | `UPDATE tasks SET status='paused' WHERE status='downloading'` | 任务级状态恢复为暂停，等用户决定是否继续 |
| task_items | `UPDATE task_items SET status='paused' WHERE status='downloading'` | 子项级同样重置，保留 `.part` 与 `downloaded_bytes` |

**执行时机**：应用启动完成数据库连接初始化后、扫描队列前，作为一次原子事务执行。

**不重置为 pending 的理由**：保留 `paused` 状态让用户能区分"我主动暂停的"与"系统崩过的"，且不会在用户不知情时自动恢复下载。

### 6.3 .part 文件与 downloaded_bytes 的协同

`.part` 文件机制是单文件分块续传的物理载体，与 `downloaded_bytes` 字段协同如下：

```
[子项进入 downloading]
        │
        ▼
[计算 .part 路径 = local_path + ".part"]
        │
        ├─ .part 存在 ──► [读取 downloaded_bytes] ──► [Range 请求]
        │                                            │
        │                                            ├─ 206 (支持续传) ─► 追加写入 .part
        │                                            └─ 200 (不支持)  ─► 清空 .part，从头写
        │
        └─ .part 不存在 ──► [downloaded_bytes 重置为 0] ──► [新建 .part，从头写]
        │
        ▼
[流式接收，每 64KB 一块]
        │
        ├─ 追加写入 .part 文件
        ├─ 内存中 downloaded_bytes += chunk_len
        └─ 每 5 秒或每 1MB ──► [持久化 downloaded_bytes 到 SQLite]
        │
        ▼
[下载完成]
        │
        ├─ 校验 downloaded_bytes == total_bytes（若 total_bytes 已知）
        ├─ .part 重命名为 local_path（去掉 .part 后缀）
        ├─ status = 'completed'
        └─ 写入 local_path 字段
```

**异常处理**：
- 若持久化 `downloaded_bytes` 失败 → 仅影响续传精度，不影响当前下载，下次重试时从上次成功持久化的位置续传
- 若 `.part` 文件写入失败（磁盘满）→ 子项转 `failed`，`fail_reason = "磁盘空间不足"`

### 6.4 失败重试计数与清理

```
[单次下载失败]
       │
       ├─ HTTP 4xx（非限流）─► 直接 failed，不重试（链接无效等）
       │
       └─ 网络异常 / HTTP 5xx / 风控限流（461/412）
              │
              ▼
       [retry_count += 1]
              │
              ├─ retry_count < 3 ─► [等待 2^retry_count 秒] ─► [status 回到 pending，重新入队]
              │                     (2s / 4s / 8s 指数退避)
              │
              └─ retry_count == 3 ─► [status = failed]
                                     [fail_reason = 具体原因]
                                     [发 item_failed 信号]
                                     [停止该子项重试]
```

**清理策略**：
- `failed` 子项不自动清理，保留在数据库供用户查看失败原因
- 用户可在 UI 上"清空已完成"（仅清 `completed` 子项及其 metadata）
- 用户可手动重置 `failed` 子项：`retry_count=0`、`fail_reason=NULL`、`status='pending'`，重新入队

### 6.5 Cookie 池轮询与健康检查

```
[请求需要 Cookie]
       │
       ▼
[查询 cookies 表]  WHERE status='valid'  ORDER BY last_used ASC  LIMIT 1
       │
       ├─ 找到 ──► [使用该 Cookie 发请求]
       │             │
       │             ├─ 请求成功 ──► [fail_count = 0, last_used = now]
       │             │
       │             └─ 请求返回 461/412 ──► [fail_count += 1, last_used = now]
       │                                          │
       │                                          ├─ fail_count < 3 ─► 仍为 valid，继续参与轮询
       │                                          │
       │                                          └─ fail_count == 3 ─► [status = 'invalid']
       │                                                                [自动切换池里下一条 valid]
       │
       └─ 未找到（池空或全 invalid）─► [暂停所有任务]
                                     [弹窗："所有 Cookie 已失效，请更新"]
```

**主动健康检查**：
- 用户在 Cookie 配置页点"测试 Cookie" → 调用轻量 API 验证
- 返回 200 且 `status_code==0` → `status='valid'`、`fail_count=0`、`last_check=now`
- 否则 → `status='invalid'`、`last_check=now`，UI 显示具体错误

## 7. 数据迁移与版本管理

### 7.1 数据库版本表设计

新增 `schema_version` 表用于追踪数据库结构版本：

```sql
CREATE TABLE schema_version (
    version     INTEGER PRIMARY KEY,
    applied_at  TEXT NOT NULL,
    description TEXT
);
```

| 字段名 | 类型 | 约束 | 说明 |
|---|---|---|---|
| version | INTEGER | PRIMARY KEY | schema 版本号，单调递增（如 1, 2, 3） |
| applied_at | TEXT | NOT NULL | 该版本应用时间，ISO 8601 |
| description | TEXT | — | 版本描述，如 "v1: 初始 schema" |

### 7.2 初始化脚本逻辑

应用首次启动或检测到数据库文件不存在时，执行初始化：

```
[应用启动]
   │
   ▼
[打开数据库连接]
   │
   ▼
[PRAGMA journal_mode=WAL]
[PRAGMA foreign_keys=ON]
[PRAGMA synchronous=NORMAL]
   │
   ▼
[查询 schema_version 表是否存在]
   │
   ├─ 不存在（首次初始化）
   │     │
   │     ▼
   │  [按顺序执行 v1 建表脚本]
   │     │  ├─ CREATE TABLE tasks ...
   │     │  ├─ CREATE TABLE task_items ...
   │     │  ├─ CREATE TABLE metadata ...
   │     │  ├─ CREATE TABLE cookies ...
   │     │  ├─ CREATE TABLE config ...
   │     │  ├─ CREATE TABLE schema_version ...
   │     │  ├─ CREATE INDEX ... (所有索引)
   │     │  └─ INSERT INTO config 预定义默认值
   │     │
   │     ▼
   │  [INSERT INTO schema_version VALUES (1, now, 'v1: 初始 schema')]
   │
   └─ 存在
         │
         ▼
      [读取当前版本号 current_version]
         │
         ▼
      [对比代码中最新版本号 latest_version]
         │
         ├─ current_version == latest ─► 无需迁移，直接进入应用
         │
         └─ current_version < latest ─► [依次执行迁移脚本]
                                       (v1→v2, v2→v3, ...)
                                       每步执行后 INSERT schema_version
```

### 7.3 未来 schema 变更的迁移策略

**迁移脚本组织**：
- 每个版本一个迁移函数，按版本号顺序执行
- 每个迁移在独立事务中执行，失败则回滚
- 迁移前自动备份数据库文件（复制为 `data.db.backup.{version}`）

**向后兼容原则**：
- 优先用 `ALTER TABLE ADD COLUMN` 添加字段（SQLite 支持，且不锁表）
- 不删除字段（SQLite 不直接支持 DROP COLUMN，且老数据需保留）
- 字段语义变更通过新增字段 + 数据迁移实现，老字段保留但不再读写

**版本管理示例**（仅示例，非当前实现）：
```
v1 (当前): 初始 schema
v2 (假设): task_items 新增 priority 字段
   ├─ ALTER TABLE task_items ADD COLUMN priority INTEGER DEFAULT 0;
   └─ INSERT INTO schema_version VALUES (2, now, 'v2: 新增 priority 字段')
```

## 8. 数据安全

### 8.1 Cookie 存储安全考量

| 风险 | 当前方案 | 局限与建议 |
|---|---|---|
| Cookie 是高敏感凭据，泄露可导致账号被盗 | 以明文存于 `data.db`，依赖文件系统权限保护 | SQLite 原生不支持字段级加密；如需增强，可未来引入 `sqlcipher` 或对 `content` 字段做应用层 AES 加密（密钥需另存于 OS 凭据库） |
| 数据库文件被复制到其他机器 | 文件位于 `%APPDATA%`，受 Windows 用户目录权限保护 | 建议应用启动时校验当前用户 SID 与文件 owner 一致 |
| 日志泄漏 Cookie | 日志中不记录 Cookie 原文，仅记录 Cookie ID 与状态变更 | 测试用 Cookie 不进仓库，VCR.py 录制前擦除 `Cookie` / `Set-Cookie` 头 |
| 卸载残留 | 卸载不主动删除 `%APPDATA%` 数据，避免误删用户数据 | 提供"清除所有数据"入口供用户主动清理 |

### 8.2 数据库文件权限

- 文件位置 `%APPDATA%\DouyinCatcher\data.db` 默认继承用户目录 ACL，仅当前用户与 SYSTEM 可访问
- 应用不主动 `chmod`，依赖 Windows 默认权限
- 不在公共目录（如 `C:\` 根、共享盘）创建数据库文件

### 8.3 备份建议

| 备份场景 | 方式 | 说明 |
|---|---|---|
| schema 迁移前 | 复制 `data.db` 为 `data.db.backup.{version}` | 防迁移失败导致数据丢失 |
| 用户主动备份 | UI 提供"导出数据"按钮 → 复制 `data.db` 到用户指定路径 | 便于换机迁移 |
| 定期备份 | 不强制（YAGNI），用户可自行复制 `%APPDATA%\DouyinCatcher\` 目录 | 桌面单机应用场景数据量有限 |

> **注意**：备份时若数据库正在运行，应先执行 `PRAGMA wal_checkpoint(TRUNCATE)` 将 WAL 日志合并回主库，避免备份不完整。
