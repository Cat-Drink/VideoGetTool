## Issue 1 — 无边框窗口与自定义标题栏

- **类型**：Feature
- **严重程度**：高
- **合并的原始问题**：A

### 问题描述

当前应用使用系统原生窗口装饰（`decorations: true`），包含 Windows 系统标题栏、窗口边框、最小化/最大化/关闭按钮。用户希望实现纯无边框窗口，所有窗口控制元素由前端自定义实现。

具体需求：

1. **移除原生窗口装饰**：`tauri.conf.json` 中设置 `decorations: false`，完全去掉系统标题栏、窗口外边框、最小化/最大化/关闭原生按钮
2. **自定义标题栏**：前端实现顶部标题栏区域，包含：
   - 应用图标 + 名称（左）
   - 窗口控制按钮（最小化、最大化/还原、关闭）（右）
   - 拖拽区域（`data-tauri-drag-region`）支持窗口拖拽
3. **设置按钮迁移至右上角**：将当前位于左侧导航栏的"设置"按钮，改为在自定义标题栏右侧放置齿轮图标按钮
4. **设置页面改为向左划出式面板**：点击设置按钮 → 从右侧向左滑出设置面板（覆盖层/侧边栏），而非切换页面路由；左上角有退出按钮关闭面板
5. **Cookie 配置页面同理**：当前 Cookie 页面为独立路由页面，改为可从设置面板中访问的侧滑面板，或保持独立路由但使用相同侧滑交互

### 原因分析

- **根因**：`frontend/src-tauri/tauri.conf.json` 中 `app.windows[0].decorations` 当前为 `true`（默认值），未配置无边框
- 当前布局：`AppShell.tsx` 使用左侧导航栏（`NavBar`）+ 右侧内容区（`Outlet`）的两栏布局
- 设置页面和 Cookie 页面均为独立路由页面（`/settings`、`/cookie`），切换时跳转路由

### 改进措施

**措施 1：Tauri 配置修改**

修改 `frontend/src-tauri/tauri.conf.json`：
```json
{
  "app": {
    "windows": [{
      "decorations": false,
      // 保留其他配置
    }]
  }
}
```

**措施 2：创建自定义标题栏组件**

新建 `frontend/src/components/app/TitleBar.tsx`：
- 左侧：应用图标 + "撷风拾影" 文字（可点击回到首页）
- 中间：预留拖拽区域（`data-tauri-drag-region`）
- 右侧：设置按钮（齿轮图标）+ 最小化按钮 + 最大化/还原按钮 + 关闭按钮
- 使用 Tauri v2 API：`@tauri-apps/api/window` 的 `getCurrentWindow().minimize()`, `toggleMaximize()`, `close()`, `isMaximized()`

**措施 3：修改 AppShell 布局**

移除左侧导航栏，改为顶部标题栏布局：
- 原导航栏功能迁移到顶部标题栏下方（或改为横向标签栏）
- 或保留侧边栏但压缩宽度，标题栏覆盖顶部

**措施 4：设置页面改为侧滑面板**

- 设置页面不再作为独立路由，改为 `AppShell` 中的覆盖层组件
- 从右侧滑入（CSS `translateX` 动画），覆盖层背景半透明
- 左上角有"← 返回"按钮关闭面板
- 设置面板内容保持当前设置页面的功能

**措施 5：Cookie 配置页面同理**

- Cookie 页面可作为设置面板内的一个子页面，或独立的侧滑面板
- 点击 Cookie 配置项时，从右侧滑入 Cookie 管理面板

### 可行性评估

- ✅ 措施 1 改动极小（1 行配置），但需注意 Windows 下无边框窗口的阴影和圆角处理
- ✅ 措施 2 需使用 Tauri v2 API，需确认 `@tauri-apps/api/window` 的正确导入方式
- ⚠️ 措施 3 涉及布局重构，需要重新设计导航交互方式（导航栏从侧边改为顶部或保留侧边但缩短）
- ⚠️ 措施 4 和 5 涉及路由架构变更，需要确保状态管理和 URL 路由的兼容性
- ⚠️ 无边框窗口在 Windows 下需要处理 Aero Snap（窗口贴边）和任务栏交互，Tauri v2 可能已有内置支持

## Issue 2 — 3D 果冻视效 UI 改造

- **类型**：UI / Feature
- **严重程度**：高
- **合并的原始问题**：B

### 问题描述

当前 UI 采用扁平化设计风格（Tailwind CSS 默认样式），用户期望改造成具有 3D 立体感的卡通休闲游戏风格按钮，类似"饱满膨胀果冻 3D 立体效果"。

视觉风格要求：
- 3D render 风格的按钮，饱满膨胀果冻 3D 立体效果
- 超大圆角矩形
- 双层软边结构：外层哑光粉色橡胶包边，内层半透蜜桃果冻渐变
- 顶部柔和圆形高光
- 黏土软质材质感
- 轻微底部悬浮软阴影
- 纯白干净背景
- 柔和漫射天光，无硬阴影
- 8K 细腻质感

### 原因分析

- 当前使用 Tailwind CSS v4 + shadcn/ui 组件库，`button.tsx` 基于 `class-variance-authority` 实现
- 所有按钮样式为扁平化设计，无 3D 效果
- 主题色为紫色（`purple-500`），需改为粉色系

### 改进措施

**措施 1：创建 3D 果冻按钮组件**

新建 `frontend/src/components/ui/jelly-button.tsx`（或修改 `button.tsx`）：

```tsx
// 核心 CSS 特征：
// - 超大圆角: border-radius: 16px-20px
// - 双层伪元素: ::before（外层粉色橡胶包边）, ::after（内层果冻渐变）
// - 顶部高光: radial-gradient 圆形高光
// - 底部悬浮阴影: box-shadow 软阴影
// - 点击动效: transform: scale(0.95) 按压效果
// - 过渡动画: transition 平滑
```

**措施 2：全局样式适配**

- 修改 `frontend/src/index.css` 或全局样式文件
- 基础背景改为纯白（`#FFFFFF`）
- 按钮颜色体系从紫色改为粉色系（`#FF9EB5`, `#FFB6C1`, `#FF69B4` 等）
- 添加全局柔和阴影和圆角主题

**措施 3：组件替换**

- 逐步将页面中的 `Button` 替换为 `JellyButton`（或通过 CSS 覆盖）
- 优先替换主要操作按钮（开始解析、开始下载、设置等）
- 次要按钮（ghost 变体）可保留扁平样式或做简化 3D 效果

**措施 4：动效增强**

- 添加悬浮（hover）动效：轻微放大 + 高光位移
- 添加点击（active）动效：压缩 + 回弹
- 考虑添加 `@keyframes` 果冻抖动动画

### 可行性评估

- ✅ 纯 CSS 实现，无需额外依赖，对性能影响小
- ⚠️ 超大圆角按钮在密集列表（如任务列表）中可能占用过多空间，需区分主按钮和列表项按钮
- ⚠️ 粉色系主题需要全站颜色体系配合，包括导航栏、标签、进度条等
- ✅ 可以使用 Tailwind CSS 的 `@apply` 或自定义组件实现，不与现有框架冲突
- ⚠️ 注意无障碍性（WCAG）：粉色系按钮的文字对比度需保证可读性

## Issue 3 — 图文选择性提交任务

- **类型**：UI / Feature
- **严重程度**：中
- **合并的原始问题**：C

### 问题描述

当前图文（`image_set`）类型的资源在解析结果列表中已支持展示，但用户在提交下载任务时，希望**可以更灵活地选择图文中的部分图片**提交下载，而非必须下载全部图片。

具体需求：
- 解析结果列表中，图文类型（`image_set`）的条目应展示图片数量
- 用户选择图文条目时，可选择仅下载部分图片（而非全部）
- 支持在提交任务前预览图文中的图片列表

### 原因分析

- 当前 `BatchFetchPage` 和 `ProfileFetchPage` 中的选择逻辑：选中一个图文条目 → 下载该条目的所有图片
- 后端 `startDownload` 接口中，`image_set` 类型的 `url` 字段以换行符分隔多个图片 URL，下载时会全部下载
- 没有提供"展开图文查看图片列表"或"选择部分图片"的 UI 交互

### 改进措施

**措施 1：图文条目展开功能**

- 在解析结果列表中，`image_set` 类型的条目增加展开按钮（▶/▼）
- 展开后显示该图文的所有图片缩略图列表
- 每张图片前有复选框，支持单独选择

**措施 2：提交任务时携带图片选择信息**

- 修改 `downloadSelected` 方法，对于 `image_set` 类型，只提交用户勾选的图片 URL
- 后端 `startDownload` 接口中，`image_set` 的 `image_urls` 字段只包含选中的图片

**措施 3：图文预览功能**

- 点击图文条目或图片缩略图，弹出预览大图（lightbox）
- 便于用户在提交前确认图片内容

### 可行性评估

- ✅ 措施 1 可通过折叠面板（collapsible）实现，UI 改动可控
- ⚠️ 措施 2 需要修改 `parseStore.downloadSelected` 和 API 调用逻辑，但后端接口已有 `image_urls` 字段支持
- ⚠️ 措施 3 为额外增强，可延后实现
- 不影响视频和长视频类型的下载流程

## Issue 4 — 图文动图/静态图片精确区分 ✅ 已实现

- **类型**：Feature
- **严重程度**：中
- **合并的原始问题**：新增动图区分需求
- **状态**：✅ 已完成（v0.3.3，PR #56）
- **关联 Issue**：#50
- **关联 PR**：#56

### 问题描述

抖音返回的部分资源存在两类问题：

图文作品中的 images 数组可能混合普通图片和动图（`clip_type=4/5`、`live_photo_type=1`、含 `images[i].video`），此前动图项被当作普通图片保存

测试链接：`https://v.douyin.com/00tC3WPkgUA/`

### 原因分析

- `downloader/downloader.py` 中的 `_extract_extension` 方法：从 URL 路径提取扩展名，若无法识别则根据类型返回 `.jpg`（image_set）或 `.mp4`（默认）
- 当前逻辑未处理动图项的视频直链，所有图文项统一走图片下载路径
- 没有区分动图/静态图片的元数据字段

### 已实施的改进措施

**措施 1：动图/静态图片精确区分（crawlers/video_parser.py）**

- `VideoInfo` 新增 `item_types: list[str]` 字段，与 `image_urls` 一一对应
- 新增 `_extract_item_types()` 判断方法，按优先级识别动图项：
  1. `live_photo_type == 1` → 动图
  2. `clip_type` 为 `4` 或 `5` → 动图
  3. `video` 字段存在且含 `play_addr` → 动图
  4. 其他 → 静态图片

**措施 2：下载层按类型处理（downloader/downloader.py）**

- `_extract_extension()` 新增 `item_subtype` 参数，动图项默认 `.mp4`
- 新增 `_get_item_subtype()` 解析 `item_types` JSON 获取子项类型
- `_reparse_single_image_url()` 改用 `merged_item_urls` 保留视频直链

**措施 3：视频直链提取（crawlers/video_parser.py）**

- `_extract_no_watermark_url` 使用单一 `play_addr.url_list[0]` 路径
- 处理 playwm→play 替换

**措施 4：前端全链路传递（frontend/src/lib/api.ts、parseStore.ts）**

- `ParsedResult` 接口新增 `itemTypes`，解析结果保存并传递到下载请求

**措施 5：数据库 schema 升级（app/database.py）**

- `task_items` 表新增 `item_types TEXT DEFAULT ''` 列（v3 迁移）

### 代码审查修复（PR #56 审查后）

- **取消三级回退链路**：`_extract_no_watermark_url` 从 `bit_rate → download_addr → play_addr` 三级回退恢复为单一 `play_addr.url_list[0]` 路径，移除 `_is_webp_url` 函数及相关辅助方法
- **删除重复方法**：移除重复定义的 `_extract_item_types`（第 2 份）
- **修复 P0 安全缺陷**：`start_download` 路由补充 `config_repo` 空值守卫
- **清理死代码**：移除未使用的 `import json / Path / config` 及 `Pillow` 依赖
- **测试解耦**：`ConnectionManager` 新增 `register_for_test` 公开方法

### 完成情况

- ✅ 全部 668 项测试通过
- ✅ PyInstaller sidecar + Tauri NSIS 安装包构建验证通过

## Issue 5 — 任务完成通知（弹窗+音效）

- **类型**：Feature
- **严重程度**：中
- **合并的原始问题**：E

### 问题描述

当前下载任务完成后，仅有任务列表中的进度条变为绿色，没有其他通知方式。用户希望：
1. 任务完成时弹出通知提示（toast 或系统通知）
2. 任务完成时播放提示音效
3. 在设置中提供通知方式和音效的开关/切换

### 原因分析

- 当前已有 `toastStore` 和 `ToastContainer` 组件，但仅在手动操作时触发（如"添加成功"）
- 任务完成事件来自 WebSocket 推送的 `item_completed` 消息，但前端未处理该消息的 UI 通知
- 没有音效播放机制
- 设置页面没有通知相关的配置项

### 改进措施

**措施 1：WebSocket 完成事件处理**

在 `DownloadPage.tsx` 的 `onWsMessage` 回调中处理 `item_completed` 和 `item_failed` 事件：
```typescript
if (msg.type === "item_completed") {
  addToast(`任务 #${msg.task_item_id} 下载完成`, "success");
  // 播放完成音效
  playNotificationSound("completed");
}
if (msg.type === "item_failed") {
  addToast(`任务 #${msg.task_item_id} 下载失败: ${msg.fail_reason}`, "error");
  // 播放失败音效
  playNotificationSound("failed");
}
```

**措施 2：音效播放实现**

- 在 `frontend/public/sounds/` 目录放置音效文件（`.mp3` 或 `.wav`）
- 创建 `frontend/src/lib/sound.ts` 工具模块：
  ```typescript
  const audioCache = new Map<string, HTMLAudioElement>();
  
  export function playSound(name: "completed" | "failed" | "notification") {
    const audio = new Audio(`/sounds/${name}.mp3`);
    audio.volume = 0.5;
    audio.play().catch(() => {}); // 静默处理自动播放策略
  }
  ```

**措施 3：设置页面通知配置**

在设置面板中增加"通知设置"区域：
- 任务完成弹窗通知：开关（默认开启）
- 任务完成音效：开关（默认开启）
- 音效选择：下拉选择（如"默认音效"、"轻柔"、"活泼"等）
- 音量控制：滑块

**措施 4：系统通知（可选增强）**

- 使用 `@tauri-apps/plugin-notification` 发送系统级通知
- 应用最小化到托盘时，系统通知比页面内 toast 更有效

### 可行性评估

- ✅ 措施 1 改动小，利用现有 WebSocket 事件和 Toast 机制
- ✅ 措施 2 音效播放使用原生 Web Audio API，无需额外依赖
- ✅ 措施 3 设置项存储到后端配置或 localStorage
- ⚠️ 措施 4 需要 Tauri 插件支持，且可能涉及权限问题
- ⚠️ 音效文件需注意版权问题，建议使用开源/免版权音效

## Issue 6 — 下载项直接打开所在文件夹 ✅ 已实现

- **类型**：Feature
- **严重程度**：低
- **合并的原始问题**：F
- **状态**：✅ 已完成（v0.3.3，PR #57）
- **关联 Issue**：#52
- **关联 PR**：#57

### 问题描述

用户在下载任务列表中，希望可以直接点击某个已完成的下载项，快速打开该文件所在的文件夹（Windows 资源管理器）。

### 原因分析

- `TaskItem` 组件中已完成项的操作按钮为 `FolderOpen` 图标，但当前该图标仅作为状态指示，未绑定点击事件
- Tauri 提供 `@tauri-apps/plugin-opener` 的 `openPath` 或 `revealItemInDir` API，可打开文件夹并选中文件
- 前端 `lib/tauri.ts` 中已有 `openExternal` 方法，但缺少打开文件夹的功能

### 改进措施

## Issue 7 — 文件校验逻辑修复

- **类型**：Bug
- **严重程度**：严重
- **合并的原始问题**：G

### 问题描述

当前校验操作（`verifyFiles`）存在误判问题：即使本地文件确实存在，校验结果仍可能显示"检验失败"。

具体现象：
- 下载完成后，点击"校验文件"按钮
- 本地文件实际存在，但校验结果显示文件缺失，状态被标记为 failed

### 原因分析

**根因 1：路径规范化问题**

- 后端 `verify_completed_files` 使用 `os.path.isfile(item.local_path)` 检查文件存在性
- `local_path` 可能存储的是相对路径、带特殊字符的路径、或 Windows 路径格式问题（如正反斜杠混用）
- 不同模块（下载器 vs 校验器）在写入和读取 `local_path` 时可能存在路径格式不一致

**根因 2：DB 中 local_path 存储异常**

- 检查 `TaskItem` 的 `local_path` 字段值是否包含正确的绝对路径
- 可能在下载完成时写入的路径与实际文件路径不一致（如临时文件重命名后路径未更新）

**根因 3：文件系统权限问题**

- 某些情况下（如安装包路径受保护），应用可能有权限读取文件但 `os.path.isfile` 返回 False

### 改进措施

**措施 1：路径规范化（高优先级）**

- 在 `_finish_download` 设置 `local_path` 时，使用 `os.path.abspath()` 和 `os.path.normpath()` 规范化路径
- 在 `verify_completed_files` 中也对 `local_path` 做同样的规范化处理
- 统一使用正斜杠（`/`）存储路径

**措施 2：双重校验（中优先级）**

- 除了 `os.path.isfile`，增加 `os.path.exists` 和文件大小检查（`os.path.getsize > 0`）
- 日志记录校验失败的详细路径信息，便于调试

**措施 3：路径日志增强（低优先级）**

- 在下载完成时记录 `local_path` 的绝对路径到日志
- 在校验时记录 `local_path` 的具体值和 `os.path.isfile` 的返回值

### 代码位置

- `backend/api/download.py` → `verify_completed_files()` 函数（约第 103-140 行）
- `downloader/downloader.py` → `_finish_download` 方法中设置 `local_path` 的位置

### 可行性评估

- ✅ 措施 1 改动最小，定位到根因即可修复
- ✅ 措施 2 和 3 增强可靠性，不影响现有功能
- ⚠️ 需要复现问题场景才能确认根因，可能需要用户配合提供日志

## Issue 8 — 版本号仍未跟随 Release 同步更新

- **类型**：Bug
- **严重程度**：低
- **合并的原始问题**：H

### 问题描述

虽然 v0.3.2 已建立了版本号自动同步机制（`VERSION_MANAGEMENT.md` 中定义的 6 个文件 + pre-commit 钩子 + CI 注入），但**前端页面中硬编码的版本号显示字符串**仍未更新，导致用户看到的版本号始终为旧版本。

具体位置：
1. `frontend/src/components/NavBar.tsx` 第 75 行：`<span>v0.3.0</span>`（底部版本号显示）
2. `frontend/src/pages/SettingsPage.tsx` 第 184 行：`版本: v0.3.0`（关于区域版本号）

### 原因分析

- **根因**：`VERSION_MANAGEMENT.md` 中定义的 6 个版本号文件清单**遗漏了前端组件中的硬编码版本号字符串**
- 当前版本号同步机制（`scripts/sync_version.py`）只覆盖以下 6 个文件：
  1. `pyproject.toml`
  2. `backend/app.py`
  3. `frontend/package.json`
  4. `frontend/src-tauri/tauri.conf.json`
  5. `frontend/src-tauri/src/lib.rs`
  6. `installer.iss`
- 但 `NavBar.tsx` 和 `SettingsPage.tsx` 中的硬编码版本号不在同步范围内
- 即使 CI 发布时自动注入版本号，也不会修改前端的 `.tsx` 文件

### 改进措施

**措施 1（推荐）：使用 Tauri 命令动态获取版本号**

- `NavBar.tsx` 和 `SettingsPage.tsx` 改为调用 `getAppVersion()` Tauri 命令获取版本号
- 在组件加载时异步获取版本号并显示
- 这样版本号始终与 Tauri 配置一致，无需手动同步

```tsx
// 在 NavBar.tsx 中
const [appVersion, setAppVersion] = useState("...");
useEffect(() => {
  getAppVersion().then(setAppVersion).catch(() => setAppVersion("0.3.2"));
}, []);
```

**措施 2（备选）：将硬编码版本号加入同步脚本**

- 修改 `scripts/sync_version.py`，增加对 `NavBar.tsx` 和 `SettingsPage.tsx` 的版本号替换规则
- 并在 `VERSION_MANAGEMENT.md` 中更新版本号维护清单（从 6 个变为 8 个）

### 可行性评估

- ✅ 措施 1 是更彻底的解决方案，避免未来再次遗漏
- ✅ 措施 1 使用现有 Tauri 命令 `get_app_version`，无需修改后端
- ⚠️ 措施 1 需要异步加载，可能短暂显示旧版本号或加载状态
- ⚠️ 措施 2 治标不治本，未来新增页面仍可能遗忘
- 不影响任何功能逻辑
