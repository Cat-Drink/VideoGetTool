# 影响分析报告：现有代码结构研究（Issue-21）

## 1. DownloadPage 的 WebSocket 消息处理

### 前端 (frontend/src/pages/DownloadPage.tsx)
- **WebSocket 连接**：通过 useWebSocket hook 建立到 ws://127.0.0.1:18989/api/ws 的连接
- **消息处理回调**：onWsMessage（第 41-50 行）监听 WsMessage，仅处理 type === "progress" 的消息，将 msg.updates 数组中的每个更新通过 applyProgressUpdate 应用到 taskStore
- **降级策略**（第 54-76 行）：当 connected === false 时，启动 2 秒间隔的 REST API 轮询（loadTasks()），作为 WebSocket 断开时的降级方案
- **当前只处理 progress 类型消息**；item_completed 和 item_failed 类型消息（后端 app.py 第 83-148 行会广播这些类型）**未被前端处理**

### 后端 WebSocket 服务 (backend/api/ws.py)
- **ConnectionManager**（第 22-60 行）：管理 WebSocket 连接池，支持 connect/disconnect/broadcast
- **/ws 端点**（第 82-119 行）：接受连接 -> 发送 {"type": "connected"} -> 监听前端消息（仅处理 ping->pong 和 subscribe->subscribed 两种客户端消息）
- **共享进度推送**（第 122-168 行）：_push_progress_updates 每 1 秒轮询数据库，查询 downloading/processing/completed/failed 状态的任务项，广播 {"type": "progress", "updates": [...]}
- **后端广播的事件类型**（来自 backend/app.py 第 83-148 行）：
  - item_completed（下载完成回调触发）
  - item_failed（下载失败回调触发）
  - progress（调度器进度回调触发，与共享轮询双重推送）

### 影响范围
- 修改 WebSocket 消息协议需同步更新：前端 useWebSocket.ts 的 WsMessage 类型、DownloadPage 的消息处理回调、后端 ws.py 的广播逻辑
- 若修改 WsMessage 类型，需检查所有消费方：DownloadPage 及未来新增的页面

## 2. SettingsPanel 的配置结构

### 前端 (frontend/src/components/app/SettingsPanel.tsx)
- **状态管理**：useState 本地管理 config, loading, saving, concurrency, appVersion, openSection
- **配置加载**：loadConfig() 调用 api.fetchConfig()，返回 ConfigResponse 类型
- **配置字段**：
  - download_dir：下载目录（字符串）
  - concurrency：并发下载数（滑块，范围 1-10，默认 3）
  - chunk_size：单文件分块大小（显示为 MB，只读展示）
  - metadata_format：元数据保存格式（JSON 复选框，CSV 禁用）
  - onboarding_done：引导完成标记
- **配置更新**：api.updateConfig({...}) 发送 POST 请求，支持部分更新
- **配置重置**：api.resetConfig() 恢复默认值
- **UI 结构**：折叠卡片式布局（SectionCard），分账号管理、下载设置、元数据设置、日志与反馈四组

### 影响范围
- 新增配置项需：1) 更新后端 backend/api/config.py 的 ConfigResponse 和 UpdateConfigRequest 模型；2) 更新前端 ConfigResponse 接口；3) 在 SettingsPanel 中添加对应 UI 组件
- 修改配置数据类型（如 concurrency 改为浮点数）需同步更新前后端类型定义

## 3. api.ts 的接口定义

### 文件位置：frontend/src/lib/api.ts
- **API_BASE**：http://127.0.0.1:18989/api
- **通用请求包装**：request<T>(path, options?)，自动设置 Content-Type JSON，处理非 200 响应

### 数据类型定义
- TaskStatus: "pending" | "downloading" | "paused" | "processing" | "completed" | "failed"
- CookieStatus: "valid" | "invalid" | "untested"
- TaskResponse: id, source_type, source_url, status, total_items, completed_items, created_at, updated_at, download_dir
- TaskItemResponse: id, task_id, aweme_id, url, title, author, type, status, downloaded_bytes, total_bytes, progress, cover_url, fail_reason, local_path
- ConfigResponse: download_dir, concurrency, chunk_size, metadata_format, onboarding_done
- CookieResponse: id, content, label, status, last_used, last_check, fail_count, created_at
- ParseResult: url, title, author, type, aweme_id, cover_url, duration, image_count, no_watermark_url, image_urls, item_video_urls, item_types, publish_time, error

### API 端点分类
1. **健康检查**：GET /health, GET /ready
2. **下载任务**：GET /download/tasks, GET /download/tasks/{id}/items, POST /download/start, POST /download/pause/{id}, POST /download/resume/{id}, POST /download/retry/{id}, POST /download/retry-all, POST /download/pause-all, POST /download/resume-all, DELETE /download/tasks/items/{id}, DELETE /download/tasks/{id}, POST /download/clear-completed, POST /download/verify
3. **爬虫**：POST /crawler/parse, POST /crawler/fetch-home
4. **Cookie**：GET /cookie/list, POST /cookie/add, POST /cookie/test/{id}, DELETE /cookie/{id}
5. **配置**：GET /config, POST /config, POST /config/reset, GET /config/{key}

### 影响范围
- 新增 API 端点需在 api.ts 中添加对应函数
- 修改接口返回结构需同步更新前端类型定义，否则 TypeScript 编译不通过
- 前端 3 个 store（taskStore, parseStore, uiInputStore）和多个页面组件依赖这些 API 函数

## 4. 后端 config.py 的模型

### 应用配置常量 (app/config.py)
- APP_DATA_DIR: %APPDATA%/VideoGetTool
- DB_PATH: {APP_DATA_DIR}/data.db
- LOG_DIR: {APP_DATA_DIR}/logs
- LOG_FILE: {LOG_DIR}/app.log
- DEFAULT_DOWNLOAD_DIR: ~/Downloads/VideoGetTool
- 默认配置值：DEFAULT_CONCURRENCY=3（1-10）、DEFAULT_CHUNK_SIZE=1MB、DEFAULT_RETRY_COUNT=3（固定）、DEFAULT_METADATA_FORMAT="json"
- DEFAULT_CONFIGS 字典将默认值聚合插入 config 表

### 后端配置 API (backend/api/config.py)
- ConfigResponse（Pydantic）：download_dir, concurrency, chunk_size, metadata_format, onboarding_done
- UpdateConfigRequest（Pydantic）：所有字段可选，支持部分更新；concurrency 更新时动态调整调度器
- GET /api/config：读取全部配置
- POST /api/config：部分更新
- POST /api/config/reset：重置默认
- GET /api/config/{key}：读取单项

### 数据库模型 (app/models.py)
- 5 个枚举：TaskStatus, TaskItemStatus, SourceType, VideoType, CookieStatus（均继承 StrEnum）
- 5 个 dataclass：Task, TaskItem, Cookie, Metadata, Config
- 关键字段：TaskItem 支持 selected_image_indices（图片级勾选 JSON 数组）、item_types（逐项媒体类型 JSON 数组）；Metadata 含完整作品元数据（点赞/评论/分享/收藏数、标签、原始 JSON）

### 应用上下文 (backend/state.py)
- AppContext 单例：持有数据库连接、所有 Repository、爬虫组件、调度器、HTTP 客户端等全局实例
- 初始化顺序在 backend/app.py 的 lifespan 中定义

### 影响范围
- 新增配置项需：1) app/config.py 添加默认值；2) backend/api/config.py 的 ConfigResponse/UpdateConfigRequest 添加字段；3) 前端 api.ts 的 ConfigResponse 同步
- 数据库模型变更需同步更新 Repository 层、API 层和前端类型定义

## 5. 关键结论与注意事项

1. 前端 WebSocket 只消费 progress 消息，item_completed/item_failed 消息被忽略 —— 若 issue-21 与通知相关，这是潜在的功能缺口
2. WebSocket 断开时有 2 秒 REST 轮询降级，连接恢复后轮询停止
3. 配置是全链路（app/config.py -> backend/api/config.py -> frontend/api.ts -> SettingsPanel）贯穿的，任何新增配置项都要走完整链路
4. 前端类型定义（api.ts）与后端 Pydantic 模型（backend/api/config.py, download.py, crawler.py）需要手动保持同步，无代码生成
