## Issue 1 — 输入框缓存生命周期优化

- **类型**：UI / Feature
- **严重程度**：中
- **合并的原始问题**：A

### 问题描述

当前输入框内容使用 `uiInputStore`（zustand + `persist` 中间件）缓存到 localStorage，切换页面后内容不会丢失。但缓存策略过于粗粒度：**无论解析是否完成，输入内容始终保留**，不符合用户预期的交互流程。

用户期望的三阶段行为：

| 阶段 | 输入框内容 | 可选项列表 |
|:---|:---|:---|
| ① 输入未解析 | ✅ 保留（用户继续编辑） | 无 |
| ② 解析完毕 | ❌ 消失 | ✅ 保留供选择 |
| ③ 提交任务 | ❌ 消失 | ✅ 保留（已提交项可移除） |

### 原因分析

- **根因**：`useUiInputStore` 使用 `persist` 中间件将输入框内容永久保存到 localStorage，且 `BatchFetchPage` 和 `ProfileFetchPage` 在解析成功时没有主动清空输入框内容。
- 代码位置：`frontend/src/store/uiInputStore.ts`（持久化存储）+ `frontend/src/pages/BatchFetchPage.tsx`（解析后未清空 `setLinks`）+ `frontend/src/pages/ProfileFetchPage.tsx`（解析后未清空 `setHomeUrl`）

### 改进措施

1. 在 `parseUrls()` 和 `fetchHome()` 成功后，自动调用 `setBatchLinks("")` / `setProfileHomeUrl("")` 清空输入框内容
2. 保留 `uiInputStore` 的 persist 机制，但将"清空输入框"作为解析成功流程的一部分
3. 可选项列表（`batchResults` / `profileResults`）不受影响，保持独立状态

### 可行性评估

- ✅ **可行**，改动量小（2 个页面各加 1 行代码）
- ✅ 不影响其他功能
- ⚠️ 注意：如果用户希望"解析后还能回头编辑链接"，此修改会丢失输入内容，但符合用户明确提出的需求

## Issue 2 — 下载进度 & 状态同步机制异常

- **类型**：Bug
- **严重程度**：严重（数据可信度受损，用户无法判断下载真实状态）
- **合并的原始问题**：B、H

### 问题描述

此 Issue 合并了多个表象不同但根因关联的进度/状态问题：

#### 现象一：下载完成进度条不更新（原问题 B）

任务实际已下载完成（文件已写入磁盘），但进度条仍卡在 96%、97%、100% 等位置，不显示绿色完成状态。

#### 现象二：大量下载时进度条卡住（原问题 H-1）

大量任务并行下载时，部分已完成的进度条不更新，卡在某个百分比不动。

> 注：用户提到的"服务未连接"提示（页面右上角红色圆点）与此处进度条卡住是**两个独立的问题**。
> "服务未连接"指的是前端与后端之间的 **WebSocket 实时推送通道断开**，此时进度条不会自动更新，但后端下载仍在进行。
> 用户手动点击刷新按钮（REST API 重新拉取数据）即可恢复进度显示。详见 Issue 2 备注部分。

#### 现象三：刷新按钮将所有任务标记为已完成，但实际文件缺失（原问题 H-2）

- 用户点击刷新按钮（`loadTasks`）后，所有 11 个任务都显示为绿色已完成
- 但检查下载路径，实际只有 9 个视频文件存在
- 说明 **DB 状态标记为 completed 但文件实际未写入或已被删除**

#### 现象四：重试操作无进度条变化，但文件直接出现（原问题 H-3）

- 对已完成的绿色任务点击重试，进度条不发生变化（仍显示绿色 100%）
- 一段时间后文件出现在本地，但用户完全看不到下载过程

#### 现象五：已完成任务重试时进度条不反映进度（原问题 H-4）

将已下载的视频文件从本地移除后，点击重试，进度条不变化，但文件直接获取到本地，没有下载进度体现。

### 原因分析

#### 现象一 ~ 三的根因

**根因 1：WebSocket 进度推送可靠性不足**

- `ProgressReporter._report_loop` 每 500ms flush 一次，调用 `on_progress` 回调
- `_on_progress` 回调（`backend/app.py`）使用 `asyncio.create_task(broadcast(...))` **不 await**——如果广播抛出异常，静默丢失
- WebSocket 的 `_push_progress_updates` 协程每 1 秒轮询 DB 推送，与实时回调存在竞争：如果 DB 尚未写入"最终状态"而轮询先到，前端可能收到过时数据
- WebSocket 断开后前端无 fallback 机制，实时进度彻底中断

**根因 2：`loadTasks` 合并逻辑掩盖了真实状态**

前端 `loadTasks` 的合并逻辑（`taskStore.ts:100-116`）：
```typescript
// 如果已有项是终态（completed/failed），且新的不是或一样，保留已有
if (isTerminal(existing.status) && !isTerminal(fresh.status)) {
    return existing;
}
```
该逻辑本意是防止刷新时回退已完成的状态，但副作用是：**一旦状态被错误标记为 completed，即使后续刷新得到真实状态，前端也不会更新**。

**根因 3：DB 状态与文件系统不一致**

- `Downloader` 在下载完成后会将 status 更新为 `completed`，但文件写入可能存在延迟或写入后又被外部删除
- 没有**文件存在性校验**机制：刷新时只查 DB 状态，不验证文件是否真实存在

#### 现象四 ~ 五的根因

**根因 4：`loadTasks` 合并逻辑阻止了重试后的状态刷新**

重试流程：后端 `reset_for_retry` → DB 状态变为 `pending` → `add_task_items` 入队 → 前端 `loadTasks()` 重新加载

但 `loadTasks` 合并逻辑中，`existing`（当前 store 中的 item）状态为 `completed`，`fresh`（API 新加载的）状态为 `pending`，由于 `isTerminal(existing.status)` 为 true 而 `isTerminal(fresh.status)` 为 false，**返回了旧的 completed 状态**，导致前端始终显示绿色 100%，看不到进度变化。

**根因 5：`retryItem` 调用 `loadTasks` 时机不当**

`retryItem` 在调用 API 后立即调用 `loadTasks`，此时后端虽然已重置状态，但下载可能尚未开始或刚刚开始，前端加载到的数据可能还是过渡状态。

### 改进措施

**措施 1：修复 `loadTasks` 合并逻辑（高优先级）**

- 对 retry 场景特殊处理：当 `fresh.status === "pending"` 且 `existing.status === "completed"` 时，不应保留旧状态，应使用新状态
- 或增加时间戳判断：如果 `fresh.updated_at > existing.updated_at`，使用 fresh 数据
- 简化方案：去掉此合并逻辑，直接使用 fresh 数据（API 是权威数据源）

**措施 2：增加文件存在性校验（中优先级）**

- `loadTasks` 时，对 `status === "completed"` 的项校验 `local_path` 文件是否存在
- 若文件不存在，自动将状态重置为 `failed`（或 `pending`）并提示用户
- 后端可新增 `/api/download/verify` 端点批量校验

**措施 3：增强 WebSocket 进度可靠性（中优先级）**

- `_on_progress` 回调中添加 try-catch 和重试机制
- WebSocket 断开时前端降级为轮询 REST API（每 2 秒调用 `loadTasks`）
- 统一进度推送路径：避免实时回调与轮询推送两条路径竞争

**措施 4：`retry` 流程优化（低优先级）**

- `retryItem` 调用 API 后，不立即调用 `loadTasks`，而是将本地状态改为 `pending`，等待 WebSocket 推送更新
- 或后端在 `retry_download` 接口返回后，前端主动将本地状态置为 `pending`，进度 0%

### 可行性评估

- ✅ 措施 1 改动小、风险低，建议优先修复
- ✅ 措施 2 需要后端新增 API，但逻辑独立，不影响其他功能
- ✅ 措施 3 中 WebSocket 降级轮询可能增加后端负载，但影响可控
- ✅ 措施 4 中本地状态立即更新可以显著改善用户体验
- ⚠️ 措施 3 中统一进度推送路径涉及较大重构，建议分步实施

### 备注：关于"服务未连接"指示器

页面右上角显示的"服务未连接"（红色圆点）或"已连接"（绿色圆点），反映的是**前端到后端 WebSocket 实时推送通道的连接状态**，并非后端服务是否在运行。

- **"已连接"（绿色）**：WebSocket 通道正常，后端会**实时推送**下载进度、完成/失败事件到前端，进度条自动更新。
- **"服务未连接"（红色）**：WebSocket 通道断开，实时推送中断，进度条**不会自动更新**。但此时：
  - 后端下载任务**仍在正常进行**，不会中断
  - 用户点击右上角的**刷新按钮**（🔄），会通过 REST API 重新拉取全部数据，手动恢复进度显示
  - 断开后前端会自动每 3 秒尝试重连

常见断连原因：后端重启（如调试模式文件变更自动 reload）、网络临时波动、休眠恢复后。

**结论**：该指示器只是一个实时性提示，不影响下载功能本身。用户看到"服务未连接"时，点击刷新按钮即可查看最新进度，无需担心任务丢失。

## Issue 3 — 解析能力增强：发布时间 + 链接类型扩展

- **类型**：Feature
- **严重程度**：中
- **合并的原始问题**：C、D

### 问题描述

#### 需求一：抓取信息包含发布时间（原问题 C）

当前解析结果中缺少作品的发布时间字段，用户无法根据时间筛选或判断作品新旧。

当前 `ParsedURLResponse` 模型（`backend/api/crawler.py`）缺少 `published_at` 字段。
前端 `ParsedResult` 接口（`frontend/src/store/parseStore.ts`）也缺少相应字段。

#### 需求二：支持更多抖音链接类型（原问题 D）

**类型 1：直播视频链接** `https://www.douyin.com/vsdetail/7670065390316114953`

- 直播回放/录播视频，URL 路径为 `/vsdetail/` 而非 `/video/`
- 用户已指出可能需**灯牌等级**才能获取，即存在权限限制
- 后端 `URLParser` 需识别 `/vsdetail/` 路径并提取 `aweme_id`

**类型 2：图文合辑/多短视频合并链接**（如抖音分享的混合内容链接）

- 用户给出的示例类似"用 AI 做视频动效分镜"的分享链接，实际是多个短视频片段合并
- 这类链接的分享格式是 `v.douyin.com` 短链，跳转后可能是合集（mix）页面
- 需要识别是否为合集类型，并解析合集中的所有视频

### 原因分析

#### 发布时间缺失

- `VideoParser.parse_video()` 返回的 `VideoInfo` 中可能包含 `create_time` 或 `published_at` 字段，但当前 `ParsedURLResponse` 模型未暴露该字段
- 前端 `ParsedResult` 接口也未定义发布时间字段

#### 链接类型不完整

- `URLParser` 当前可能只识别 `/video/`、`/note/`、`/user/` 等路径模式
- `/vsdetail/`（直播回放）路径未在 `URLParser` 的白名单中
- 合集/合辑链接（mix）的解析逻辑缺失

### 改进措施

**措施 1：增加发布时间字段**

1. 后端 `ParsedURLResponse` 增加 `published_at: str | None` 字段
2. `VideoParser` 从抖音 API 的 `create_time` 字段获取时间戳，转为可读格式
3. 前端 `ParsedResult` 接口增加 `publishedAt` 字段
4. 前端展示列表增加发布时间列（可选显示）

**措施 2：扩展链接类型支持**

1. `URLParser` 增加 `/vsdetail/` 路径识别，提取 `aweme_id`
2. 对 `vsdetail` 类型，调用 `VideoParser.parse_video()` 获取详情（同普通视频）
3. 调研合集（mix）链接的解析方式：可能需要调用合集详情 API 获取所有子视频
4. 对需要灯牌等级的资源，在解析失败时给出明确提示（如"该直播回放需要粉丝灯牌等级"）

### 可行性评估

- ✅ 发布时间字段：改动小，前端后端各加一个字段即可
- ✅ `/vsdetail/` 支持：URLParser 加一个路径规则即可，解析逻辑复用
- ⚠️ 合集解析：需要研究抖音合集 API 的调用方式，可能涉及新的接口和数据结构，工作量大
- ⚠️ 灯牌等级限制：属于抖音平台限制，应用层面无法绕过，只能给出友好提示
- 不影响其他功能

## Issue 4 — 解析结果管理优化：追加模式 + 批量删除

- **类型**：Feature
- **严重程度**：中
- **合并的原始问题**：E、G

### 问题描述

#### 需求一：解析结果应追加而非覆盖（原问题 G）

当前行为：每次解析都会**覆盖**之前的结果。

- 第一次解析 5 条 → `batchResults` 显示 5 条
- 第二次解析 5 条 → `batchResults` 刷新为 5 条（第一次的 5 条丢失）
- 期望：第二次解析后应显示 10 条（追加模式）

代码位置：`parseStore.ts:61` 中 `parseUrls` 方法：
```typescript
parseUrls: async (urls: string[]) => {
    set({ batchLoading: true, batchError: null, batchResults: [] });  // ← 这里清空了
    // ...
    set({ batchResults: results, batchLoading: false });  // ← 直接替换
},
```

同样问题在 `fetchHome` 方法中（`parseStore.ts:98`）：
```typescript
set({ profileLoading: true, profileError: null, profileResults: [] });  // ← 清空
```

#### 需求二：解析结果列表支持批量删除选中项（原问题 E）

当前解析结果列表只有复选框（选择后下载），没有"删除选中项"功能。

用户期望：在待提交任务列表中，可以**选中一些项，然后批量删除**，只保留真正想下载的条目。

### 原因分析

#### 追加模式缺失

- `parseUrls` 和 `fetchHome` 在开始时将结果数组置空（`[]`），导致每次解析都是全新替换
- 设计上假设"一次解析一次处理"，没有考虑多次解析累积的场景

#### 批量删除缺失

- 前端已有 `removeBatchItems` 和 `removeProfileItems` 方法，但 UI 上没有对应的删除按钮
- 底部操作栏只有"开始下载"，缺少"删除选中"的入口

### 改进措施

**措施 1：解析结果改为追加模式**

修改 `parseStore.ts`：

```typescript
// parseUrls 改为追加
parseUrls: async (urls: string[]) => {
    set({ batchLoading: true, batchError: null });  // 不再清空 batchResults
    try {
        const rawResults = await api.parseUrls(urls);
        const results: ParsedResult[] = rawResults.map((r, i) => ({
            // ... 映射逻辑
        }));
        set((state) => ({
            batchResults: [...state.batchResults, ...results],  // 追加
            batchLoading: false,
        }));
    } catch (e) {
        // ...
    }
},

// fetchHome 同样改为追加
fetchHome: async (url: string, maxItems = 50) => {
    set({ profileLoading: true, profileError: null });  // 不再清空 profileResults
    // ...
    set((state) => ({
        profileResults: [...state.profileResults, ...results],  // 追加
        profileLoading: false,
    }));
},
```

⚠️ 注意：
- 追加模式下，`index` 字段需要基于当前总长度重新计算，不能简单使用 `i`
- 需要增加"清空结果"按钮，让用户可以主动清空累积的结果
- 主页抓取追加可能产生重复项（同一用户多次抓取），需考虑去重

**措施 2：增加批量删除功能**

1. 底部操作栏新增"删除选中"按钮
2. 点击后确认对话框，确认后调用 `removeBatchItems` / `removeProfileItems`
3. 复用已有的 `removeBatchItems(indices)` 和 `removeProfileItems(indices)` 方法

### 可行性评估

- ✅ 追加模式：改动集中在 `parseStore.ts`，不涉及后端
- ⚠️ 追加模式需注意 index 计算和去重逻辑
- ✅ 批量删除：UI 改动小，后端无需修改
- 不影响其他功能

## Issue 5 — 应用版本号未同步更新

- **类型**：Bug
- **严重程度**：低
- **合并的原始问题**：F

### 问题描述

应用已从 v0.3.0 推进到 v0.3.1，但打包生成的应用内版本号仍显示 v0.3.0。

### 原因分析

版本号定义在多个文件中，但发布时未同步更新所有文件：

| 文件 | 当前值 | 应更新为 |
|:---|:---:|:---:|
| `frontend/src-tauri/tauri.conf.json` → `version` | `"0.3.0"` | `"0.3.1"` |
| `frontend/package.json` → `version` | `"0.3.0"` | `"0.3.1"` |
| `backend/app.py` → `FastAPI(version=...)` | `"0.3.0"` | `"0.3.1"` |
| `frontend/src-tauri/src/lib.rs` → `get_app_version()` | `"0.3.0"` | `"0.3.1"` |

需要自动化的版本号管理，避免手动更新遗漏。

### 改进措施

**短期措施：手动更新所有版本号文件**

统一更新以下文件中的版本号：

1. `frontend/src-tauri/tauri.conf.json` → `version` 字段

## Issue 6 — 下载队列排序改为后入先出

- **类型**：UI / Feature
- **严重程度**：低
- **合并的原始问题**：I

### 问题描述

当前下载任务列表的排序方式为**先入先出**（FIFO）：最早添加的任务排在最前面，新加入的任务排在末尾。

用户期望：**后入先出**（LIFO）——新加入的下载任务排在列表最顶端，方便用户第一时间看到并操作最新添加的任务。

### 原因分析

- `taskStore.items` 的排序由后端 API 返回顺序决定（`GET /api/download/tasks/{task_id}/items`）
- 后端 `TaskItemRepository.get_by_task()` 返回的列表顺序取决于 SQL 查询（可能是按 `id` 升序）
- 前端没有对 `items` 做排序处理，直接按 API 返回顺序渲染

### 改进措施

**方案一：前端排序（推荐，改动最小）**

在 `taskStore.loadTasks` 中将 items 按 `id` 降序排列：

```typescript
// 合并后按 id 降序排列（新任务排最前）
items: merged.sort((a, b) => b.id - a.id),
```

**方案二：后端排序**

- 修改 `TaskItemRepository.get_by_task()` 的 SQL 查询，增加 `ORDER BY id DESC`
- 或新增 `get_by_task_desc()` 方法

### 可行性评估

- ✅ 方案一改动量极小（1 行代码），不影响后端逻辑
- ✅ 方案二更彻底，但也需要前端配合
- ⚠️ 排序变更不影响任何功能逻辑，仅改变展示顺序

## Issue 7 — 系统托盘支持：关闭最小化 + 图标去重

- **类型**：Feature
- **严重程度**：中
- **合并的原始问题**：J

### 问题描述

#### 问题一：点击关闭窗口时直接退出进程（原问题 J-1）

当前行为：点击窗口右上角的关闭按钮（X），应用直接退出进程，后端 sidecar 也被终止。
期望行为：点击关闭按钮应最小化到系统托盘，应用在后台继续运行；用户可通过托盘菜单"退出"彻底关闭。

#### 问题二：系统托盘有两个应用图标活跃（原问题 J-2）

打开应用后，在系统托盘区域观察到两个相同的应用图标，说明 TrayIcon 被创建了两次或存在重复注册。

### 原因分析

#### 关闭直接退出

在 `frontend/src-tauri/src/lib.rs` 中：

- `TrayIconBuilder` 已创建并配置了托盘图标和菜单（"显示窗口"、"退出"）
- 但窗口关闭事件（`on_window_event`）未做拦截处理
- 默认行为：关闭窗口 = 退出应用
- Tauri 的 `RunEvent::ExitRequested` 事件虽然被监听，但窗口关闭时直接触发了退出流程

需要：
1. 监听 `on_window_event` 中的 `CloseRequested` 事件
2. 阻止默认关闭行为，改为隐藏窗口（`window.hide()`）
3. 仅在用户点击托盘菜单"退出"时执行 `app.exit(0)`

#### 托盘图标重复

可能原因：

1. **Tauri v2 的默认行为**：Tauri v2 可能在某些配置下自动创建一个默认托盘图标，加上自定义的 `TrayIconBuilder` 就变成了两个
2. **窗口状态插件**：`tauri_plugin_window_state` 插件在恢复窗口状态时可能触发了额外的托盘创建
3. **应用重启残留**：前一次进程的托盘图标未被清理，新进程又创建了一个

### 改进措施

**措施 1：拦截窗口关闭事件，改为隐藏到托盘**

修改 `frontend/src-tauri/src/lib.rs`：

```rust
// 在 setup 中或 builder 上添加窗口事件监听
.on_window_event(|window, event| {
    if let tauri::WindowEvent::CloseRequested { api, .. } = event {
        // 阻止关闭窗口，改为隐藏到托盘
        api.prevent_close();
        let _ = window.hide();
    }
})
```

**措施 2：排查并修复双图标问题**

- 检查 `tauri.conf.json` 中 `app.trayIcon` 配置是否与 `TrayIconBuilder` 冲突
- 检查 `tauri_plugin_window_state` 插件是否自动创建了托盘图标
- 在 `TrayIconBuilder` 中设置唯一 ID（如 `"main-tray"`）避免重复
- 在 `setup()` 入口处添加日志，确认 `TrayIconBuilder.build()` 只被调用一次

**措施 3：在托盘"显示窗口"时恢复窗口状态**

当前 `show` 菜单项已实现 `window.show()` 和 `window.set_focus()`，但需要确保窗口在被隐藏后能正确恢复位置和大小（`tauri_plugin_window_state` 插件应已处理）。

### 可行性评估

- ✅ 措施 1 是标准 Tauri 模式，改动小、可靠
- ⚠️ 措施 2 需要排查具体原因，Tauri v2 的托盘行为可能与 v1 不同
- ✅ 不影响其他功能
- ⚠️ 注意：Windows 平台下，隐藏窗口后需要确保 sidecar 后端进程继续运行（当前已通过 `app.manage(SidecarChild(...))` 管理，生命周期绑定到 app 而非窗口，所以应正常工作）
